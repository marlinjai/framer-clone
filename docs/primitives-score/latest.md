What each cell means:

- **Format stores it:** the entry is written into a node, survives `ComponentModel.create`, a snapshot, JSON and a second create, and is read back unchanged through `getResolvedProps`. For a selector, at-rule, media feature or event handler the bytes alone prove nothing (props are opaque JSON and hold anything), so it also needs a reader that gives it a meaning: it has to reach the page. An attribute named like a CSS property comes back as a style, which counts as stored.
- **Published renderer emits it:** the node goes through `applyResponsiveStyles` and `renderComponentNode`. An element or attribute must be in the markup, an attribute on the opening tag of its own element, and when that element is missing the attribute takes the element's gap. An SVG or MathML entry sits inside its root element and Chromium must parse the tag into that namespace. A CSS property must be there both ways a declaration reaches a page: inline, and in the page stylesheet as a responsive value, with `initial` as the value. A value row does the same with its sample on a host property. A WAI-ARIA pattern must pass its keyboard contract in real Chromium.
- **Editor canvas shows it:** the same entry through the real `ComponentRenderer` with a real store, rendered to markup. An SVG attribute that arrives as a style declaration passes, because SVG maps those to the same property; an HTML one is `attribute-read-as-style`. A WAI-ARIA pattern runs its contract on the mounted editor instead: the real `EditorApp` in Chromium with the tree on a page, its server edge stubbed, in the Interact tool, where the page runs. So does the proof of an event row. A contract that passes when published and fails there is `canvas-editor-context`. A rule row renders the canvas sheet beside it and reads the text that sheet holds: pointer states and conditions on the editor must be dead until previewed, and the frame must answer a width.
- **Panel can edit it:** the real `RightSidebar` is mounted for a node of each component category and every control is operated. A key counts only if an action changed it in the node, and an attribute only on the tag the action changed it on. An element counts when a palette entry produces it or a panel action sets it. A pattern counts when every tag and prop it uses does: its stored behaviour, with the rules on a state or the gate, when the palette places that preset, and a plain rule through the raw field. A value row counts only for the kinds the driver types (a length, a color, a number) and when a control kept what was typed.
- **AI generator can produce it:** `validateGeneration` is given a node with the entry, and the entry must still be there afterwards. A tag rewritten to `div` is a fail. A value row needs the exact value back. A sample on a host property outside the allowlist fails as `ai-style-allowlist`, so it says nothing about the value. A rule row needs its stored rule back unchanged, and carries the note `accepted, not taught` unless the prompt teaches that form. A rule that reads a visitor or looks past its node is `ai-rule-refused`: that is a safety decision, not a missing feature.
- **A reusable component row** is a promise of the format, not a web standard entry. Format: it survives the snapshot round trip with a reader. Published: it is emitted through `renderPublishedPage`. Canvas: it renders through the real `ComponentRenderer`. Panel: it changes through the real section. AI: it survives `validateGeneration`. A pass here proves less than it reads: the corpus is the test.

The panel writes 528 style keys and 155 other props across every category. Palette tags: `a`, `button`, `div`, `img`, `p`.

Of the panel's passing cells, 136 are the `raw field`: a person typed the CSS, and no control exists for it. They pass, and they say less than a control would.
Of the AI generator's passing cells, 89 are `accepted, not taught`: the validator keeps the rule, and the prompt never asks for it. They pass, and they say the generator can write the form, not that it will.

## Parity corpus

Each fixture is a page written against the browser's own defaults, so its replica sits on a site that chose that base (Page base in Site settings, `src/lib/site/pageBase.ts`), on the same sheets a visitor of that site gets. "Default base" is the same replica on the default page base, where the reset stands: its untouched page at each breakpoint, all three checks at once. No author could close that column on the nodes, because most of what differs is `tab-size`, font smoothing and the border style and colour of every borderless element. It is reported and not ratcheted. Each fixture is an original next to the closest node tree, rendered through the published path, in Playwright's Chromium, at the three default breakpoints and in each scripted state. A check fails on more than 0.1 percent of pixels differing (per-pixel threshold 0.1), any computed style difference on matched elements including `::before` and `::after` content, or any difference in the accessibility tree. A fixture passes only when every check passes. The interaction check is not independent: it passes when the other three pass in that scripted state, so one failed state counts up to four times in the check totals and in a gap's cost. A check that fails on the published page but passes on the same output with no root layout sheet at all goes to `published-base`. Any other difference goes to a gap that comes from the state it appeared in or from the fixture's declared purpose, except that text missing from an untouched page is `mixed-text` and a differing `::before` or `::after` is `selector-styles`.

## BusBasis pages (held out)

The stop condition of the primitive stream is that every BusBasis page passes, so these are real pages of basiscampberlin.de frozen from the live site, not small fixtures, and 9 more page types are listed below as not captured. Each tree is lifted mechanically by `test/score/busbasis/lift.ts`, one rule set for all pages, with no page-specific code. The checks are the corpus checks, except that custom properties are not compared (their effect shows in what reads them) and images and video are same-size placeholders, so image content is not compared. A page also fails on everything under "needs": a page that matches pixel for pixel is not that page while what it exists for does not work. The files are held out: nothing in `test/score/corpus/busbasis` changes without a new capture, and the run stops when a hash does not match.

A BusBasis page brings its own base: the storefront's Tailwind reset is in its sheet, and the lift writes it onto every node. So, like the corpus, its replica sits on a site with Browser defaults as its page base, where the reset of the root layout steps aside and the page's own base stands. "Default base" is the same replica on the default page base, its untouched page at each breakpoint, all three checks at once, reported and not ratcheted: there every element inherits the root layout's font smoothing and `<option>` loses its padding, which no node of this page sets. A difference that goes away on the same output with no root layout sheet at all is `published-base`, measured per property.

It says how much of the lists a gap covers, not how often a real page hits it: text mixed with elements has no matrix row at all and only one fixture so far, so its low cost says nothing about how common it is. ## What this does not measure yet

- **CSS value grammar per property.** A value row is one sample on one host property, so it proves the value type survives, not that every property takes every type. Named syntaxes in mdn-data below the level of a type (such as `<bg-size>`) have no row.
- **Attribute value grammar.** An attribute row proves the name reaches the page with one value. SVG and MathML samples are not checked for meaning, MathML attribute value notes have no row, and ARIA roles and attributes are still one sample each.
- **Handlers on `body` and `window`** (`onbeforeunload`, `onhashchange`, ...), because `body` is excluded. An event row is one stored action run once from one real cause, in Chromium, on the published path with the runtime bundled in. On the canvas the same action runs from the same cause on the mounted editor in the Interact tool. In the panel it still asks the old question until slice B11.
- **Canvas markup beyond the patterns.** Only the WAI-ARIA rows run on the mounted editor, and only by keyboard: their contracts never click, so a click that selects shows up through Enter and Space. Everything else in the canvas column is rendered to markup. `canvasRules.score.ts` runs stored rules on the mounted editor with a real pointer, as a gate that counts for no row, so a canvas cell for a rule says the text is in the sheet and that gate says what the text does. Dragging under a rule is not tested.
- **Whether a panel control is any good.** A key counts as editable when a control changed it, whatever range or units that control offers. Only the properties panel and the palette are covered: the quick toolbar, context menus and the Layers panel were searched for tag changes and none found, not driven.
- **The whole published page.** The corpus uses `applyResponsiveStyles` and `renderComponentNode`, without `hydrateBindings`, effects, the sticky bar, or the consent and font wrappers, and only in Chromium. The page around it is real: the sheet of a production build (`test/score/data/published-base.css`, refreshed by `pnpm score:refresh-base`), and the mounted editor sits on the same sheet. Its utilities also follow classes in `test` and `docs`, which the deployed image does not scan, so it can hold a few the live sheet lacks.
- **WAI-ARIA conformance.** A contract is the primary keyboard path of a pattern, not its whole page in the Guide.
- **Page-level items:** a site theme has rows (`test/score/pageItems.score.ts`): format, published in Chromium, and the canvas on the mounted editor, its theme set through the project and measured on the frame, with what lies outside the frames checked unchanged. The preview, the panel (slice T4) and the AI (slice T5) are not measured, and neither is WebKit on the canvas. Head tags and page-wide scripts have no rows yet, and script and style elements are excluded with a reason.
- **Script on the BusBasis pages.** A frozen page holds no script, so menus, modals, filters and the gallery cannot run on the original. They stand under "needs" as failures rather than as compared states. A page is frozen in one state: logged out, no cart, the first visit.
- **React import beyond static JSX and Tailwind.** Props as inputs, `cva` tables, entries, hooks, Radix and the AI rebuild step of the plan are not built, so the real components read "not imported", honestly. The import score runs in Chromium only, on the default frames, and with no dark mode state.
